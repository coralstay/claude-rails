# 0. 문서 정보

이 문서는 claude-code-agile-hooks의 설계 문서다. 상위 문서는 최상위 [Sigkill Foundry 설계 문서][foundry]이고,
이 컴포넌트는 그 3.03 컴포넌트 명세 §2(규율 레이어)를 구현한다. 스펙 주도 개발(SDD)을 따른다 — 구현은
이 명세에서 도출하고, 명세와 코드가 어긋나면 명세를 먼저 고친 뒤 코드를 맞춘다.

## 문서 구성

설계 문서는 최상위 Sigkill Foundry와 같은 다섯 문서로 이어진다. 문서마다 하나의 질문에 답하고, 앞 문서의
답이 뒤 문서의 입력이 된다.

| 번호 | 문서 | 답하는 질문 |
| --- | --- | --- |
| 1 | 프로젝트 제안서 | 왜 만들고, 무엇을 어디까지 하는가 |
| 2 | 요구사항 명세서 | 무엇을 만족해야 하는가 |
| 3 | 아키텍처 설계서 | 어떻게 구성되고 동작하는가 |
| 4 | 구현 계획서 | 어떤 순서로 만들고, 무엇으로 판정하는가 |
| 5 | 구현 결과 보고서 | 무엇을 만들었고, 판정은 어떻게 나왔는가 |

장은 `문서 번호.장 번호`로 가리킨다 (예: 3.01 시스템 구성). 장 안의 절은 `§`로 가리킨다 (예: 3.01 §2).
최상위 문서의 장은 앞에 "최상위"를 붙여 가리킨다 (예: 최상위 3.03 §2, 최상위 1.02 P6).

## 규범 용어

| 표현 | 뜻 |
| --- | --- |
| 반드시 ~한다 (MUST) | 어기면 명세 위반이다 |
| ~해야 한다 (SHOULD) | 어길 때는 이유를 3.05 설계 결정에 남긴다 |
| ~할 수 있다 (MAY) | 선택 사항이다 |

## ID 체계

| 대상 | 형식 | 둘 곳 | 비고 |
| --- | --- | --- | --- |
| 원칙 | `P-<번호>` | 1.02 | 최상위 원칙(`P1` ~ `P9`)과 구분하려고 하이픈을 넣는다 |
| 목표 | 최상위 `G-n`을 그대로 쓴다 | 1.03 | 이 저장소는 목표를 새로 만들지 않는다. 주로 최상위 G-3(레일로 규율 강제) · G-4(계측과 감사 추적)에 이바지한다 |
| 요구사항 | `RAIL-<세 자리 번호>` · `RAIL-<세 자리 번호>.<번호>` | 2.03 · 2.04 | 아래 추적 규칙 참고 |
| 품질 요구사항 | 최상위 `NFR-<세 자리 번호>`를 그대로 쓴다 | 2.04 | 예: NFR-016(훅 독립성) |
| 설계 결정 | `ADR-<번호>` | 3.05 | 원천은 `backlog/decisions/decision-<번호>` |
| 미결 사항 | `Q-<번호>` | 4.03 | 아직 정하지 않은 값은 `TBD(Q-n)`으로 적는다. 최상위 미결은 "최상위 Q-n"으로 가리킨다 |

- 요구사항 번호는 재사용하지 않는다.
- 모든 요구사항은 수용 기준을 하나 이상 가진다(4.02).

## 추적 규칙

요구사항 접두어 `RAIL`은 최상위 2.03 기능 요구사항의 claude-code-agile-hooks 영역과 같다. 그래서 이
저장소의 요구사항은 최상위 요구사항과 같은 ID 공간에 있다.

| 이 저장소의 요구사항 | 뜻 | 최상위와의 연결 |
| --- | --- | --- |
| `RAIL-nnn` | 최상위 2.03에 정의된 요구사항 그 자체 | 같은 ID. 문장을 고치려면 최상위 2.03을 먼저 고친다 |
| `RAIL-nnn.m` | 최상위 `RAIL-nnn`을 이 저장소에서 세분한 하위 요구사항 | 부모가 `RAIL-nnn`이다. 부모 없는 하위 요구사항은 둘 수 없다 |

- 최상위에 부모가 없는 새 요구사항이 필요하면 최상위 2.03에 `RAIL-nnn`을 먼저 올린 뒤 이 저장소에서 세분한다.
- 이 저장소 안의 사슬은 최상위와 같다: 최상위 목표 `G-n` → 요구사항 `RAIL-nnn(.m)` (2.03 · 2.04) → 훅 · 인터페이스 (3.03 · 3.04) → 수용 기준 (4.02) · backlog 태스크 (4.01) → 결과 판정 (5.02). 사슬이 끊긴 항목은 둘 수 없다.
- 훅 하나는 자신이 구현하는 요구사항 ID를 3.03에 적는다. backlog 태스크 카드는 자신이 구현하는 요구사항 ID를 적는다.
- 원칙(1.02)에 어긋나는 요구사항은 둘 수 없다. 원칙을 바꾸려면 3.05 설계 결정에 결정을 먼저 남긴다. 이 저장소의 원칙은 최상위 원칙에 어긋날 수 없다.
- 계획과 다르게 구현한 것은 5.03 계획 대비 편차에 적고, 해당 설계 결정(3.05)에 연결한다.

## 편집 규칙

- 설계 내용의 원본은 이 설계 문서 하나다. 편집 원본은 Claude 앱의 문서이고, 저장소의 `design/**/*.md`는 Claude가 동기화하는 사본이다. 둘이 어긋나면 Claude 앱 문서가 맞다. 새 근거가 생기면 Claude 앱 문서를 먼저 고치고 사본을 맞춘다. Claude 앱 문서 링크는 `design/README.md` 목차 표에 둔다(아직 없는 칸은 `(링크 예정)`).
- 한 장 = 한 문서. 같은 내용을 두 장에서 고치고 있다면 한쪽을 장 참조 한 줄로 접는다.
- `README.md` · `backlog/docs` · `backlog/decisions` · `backlog/drafts` · 훅 docstring은 이 설계 문서의 원천이다. 원천은 지우지 않고, 각 장 끝 `## 원천`에 적는다.
- 다이어그램 원본은 `design/diagrams/*.dot`이다. DOT으로 먼저 쓰고, DOT으로 표현할 수 없는 것(시퀀스 등)만 mermaid(`.mmd`)로 쓴다.
- `design/build-diagrams.py`가 원본을 `design/diagrams/<이름>.svg`로 렌더한다. 색은 원본에 센티넬 hex(`design/diagrams/_common.gv`)로 적고, 빌드가 SVG 안의 CSS 변수(라이트 기본 · 다크 재정의)로 바꾼다. 빌드 전제: graphviz(`dot`), mermaid 렌더용 `npx` + 로컬 Chrome.
- 생성된 SVG는 손으로 고치지 않는다. 원본을 고치고 빌드를 다시 돌려 같은 커밋에 넣는다. 장 사본은 `![설명](../diagrams/<이름>.svg)`로 참조한다.
- 저장소 Markdown의 외부 링크는 문서 맨 아래 링크 정의 블록에 모으고, 본문은 `[표시][키]`로만 쓴다.
