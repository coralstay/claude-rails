# 세션 회고 — 훅 안전장치 감사부터 PR 머지까지 (2026-09-19)

이 문서는 2026-09-19 하루 동안 진행된 세션(claude-rails 저장소, 27개→28개 훅) 전체를
정리한 회고록이다. "이 프로젝트의 부족한 점은 어디 있을까?"라는 질문 하나에서 시작해,
독립적 재감사 → 2차 수정 → PR 머지까지 이어진 전체 사이클의 결론·의사결정·근거·결과를
남긴다. `backlog task view TASK-1`~`TASK-12 --plain`으로 각 태스크의 final summary를
개별적으로 볼 수 있지만, 이 문서는 그것들을 가로질러 "왜 이 순서로, 왜 이 방식으로
했는가"를 정리한 상위 레벨 기록이다.

## 가장 값진 교훈 — "무관한 실패"라고 말하기 전에 반드시 원인을 추적하라

이번 세션에서 가장 위험했던 순간은 새 버그를 놓친 게 아니라, **이미 있던 실패를 안일하게
"무관하다"고 두 번이나 잘못 판단**한 것이었다.

- 서브에이전트들은 `test_main_exits_cleanly_on_malformed_stdin` 3건을 여러 번 "TASK-10
  소관, 우리 변경과 무관"이라고 보고했고, 코디네이터도 처음엔 그대로 받아들였다.
- 실제로 원인을 추적해보니: 이 3개 훅은 stdin이 깨지면 `cwd=""`로 폴백하는데,
  `is_backlog_project("")`가 `os.path.join("", ".git")`을 **pytest 프로세스의 실제 OS
  작업 디렉토리 기준 상대경로**로 평가한다. 이 세션에서 `backlog init`을 이 레포 자체에
  실행하기 **전**에는 이 경로에 우연히 아무것도 없어서 조용히 넘어갔지만, 실행**한 후**
  에는 이 레포 자체가 backlog 프로젝트가 되어 `is_backlog_project("")`가 우연히 `True`가
  되고, 그 다음 `subprocess.run(cwd="")`이 빈 문자열을 유효하지 않은 경로로 취급해 죽는다.
  즉 "pytest를 어느 디렉토리에서 실행하느냐"에 따라 숨었다 나타났다 하는 **진짜 버그**였지,
  무관한 사전 존재 결함이 아니었다.
- `pre_commit_check.py`/`pre_push_check.py`가 안 죽었던 이유도 "더 안전하게 설계돼서"가
  아니라 "커밋/푸시 명령인지부터 먼저 확인하는 게이트가 우연히 먼저 있어서"였다 — TASK-10에서
  이 구분("설계상 안전" vs "우연히 안전")을 명시적으로 검증하고 기록했다.

**교훈**: "이 실패는 우리 변경과 무관하다"는 판단은 실제로 그 실패가 언제부터, 왜
존재했는지 코드를 추적해서 확인한 뒤에만 내려야 한다. 그냥 실행 환경이 같았다는 이유로
"기존부터 그랬다"고 넘기면, 세션 자신의 행동(`backlog init`)이 만든 회귀를 놓칠 수 있다.

## 핵심 의사결정 (`backlog decision` — decision-1~5로 별도 기록, 여기서는 요약만)

- **decision-1**: 커맨드 문자열 매칭 훅은 basename 정규화까지만 고치고, syscall 레벨
  강제(seccomp/eBPF)는 이 저장소의 범위 밖으로 명시적으로 제외한다.
- **decision-2**: 복붙 함수 drift는 (Kubernetes식 codegen이 아니라) REGISTRY 기반
  사후검증으로 막는다 — codegen 전환은 다음 단계 후보로 남겨둔다.
- **decision-3**: 라우터/dispatcher 훅은 도입하지 않는다 — "완전 독립형" 설계를 유지한다
  (사용자가 명시적으로 이 방향을 배제).
- **decision-4**: `git push`/원격 병합은 항상 사람이 최종 승인한다 — 로컬 브랜치 병합
  (fast-forward)까지만 자동으로 진행한다.
- **decision-5**: GitHub PR은 항상 rebase merge로 병합한다 — 이번 PR #5 1건은 merge
  commit으로 병합된 예외이며, 이후로는 원칙을 지킨다.

## 서브에이전트 운용 방식에 대한 메모

- **왜 워크트리 병렬이 아니라 브랜치 스택인가**: `git worktree`를 쓰면 `.git`이 파일이 되어
  `is_backlog_project()`의 `.git` 디렉토리 체크가 깨지고, `backlog/` 커밋 시점도 브랜치마다
  달라 태스크 상태 추적이 꼬일 위험이 컸다. 그래서 각 태스크 서브에이전트를 같은 작업
  디렉토리에서 순차로(이전 태스크의 브랜치 위에 다음 태스크 브랜치를 쌓는 방식) 실행했다 —
  병렬성은 포기했지만 backlog.md 워크플로 자체의 정합성은 지켰다.
- **매번 새 서브에이전트를 쓴 이유**: 코디네이터(나 자신)가 이미 알고 있는 맥락 때문에
  생기는 맹점을 피하기 위해서다 — 특히 재감사(5단계)에서는 의도적으로 완전히 새로운
  에이전트에게 "지금까지의 수정과 무관하게 처음 보는 사람 입장에서" 다시 보라고 지시했고,
  그 결과 코디네이터 자신이 놓쳤던 회귀 2건을 찾아냈다.
- **세션 한도로 중단됐을 때**: 같은 에이전트를 `SendMessage`로 재개하고 "이미 한 작업은
  반복하지 말 것 + TDD로 진행할 것"을 매번 지시했다(TASK-1에서 실제로 1회 발생).
